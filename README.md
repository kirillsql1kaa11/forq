# ForQ

Минималистичная текстовая соцсеть. Регистрация по почте, посты до 500 символов, лента отсортирована по новизне. Никаких алгоритмов и реалтайма.

Что умеет: посты с лайками, комментарии с ответами и вложенностью в один уровень, упоминания `@ник` с автодополнением, хештеги со страницами тегов, уведомления, восстановление пароля, установка на телефон как приложение.

## Стек

| Слой | Что используется |
| --- | --- |
| Фронт | SvelteKit 3 (SPA, `adapter-static`), Svelte 5 с рунами |
| Стили | чистый CSS, токены в `src/app.css`, тёмная тема через `prefers-color-scheme` |
| Данные | Supabase напрямую из браузера: Auth, Postgres + RLS, PostgREST, Storage |
| Хостинг | GitHub Pages или Netlify (статика из `build/`) |

Серверного кода нет: весь доступ к данным идёт через PostgREST с anon-ключом, а разграничение прав делает RLS в Postgres.

## Запуск

```bash
npm install
cp .env.example .env
npm run dev
```

В `.env` нужны два значения из дашборда Supabase (Project Settings → API Keys):

```
PUBLIC_SUPABASE_URL=https://xxxx.supabase.co
PUBLIC_SUPABASE_ANON_KEY=sb_publishable_...
```

Годится и новый ключ `sb_publishable_...`, и старый anon-JWT — оба публичные по задумке и оба попадают в бандл браузера. Ключ `service_role` / `sb_secret_...` сюда класть нельзя ни в каком виде.

Пока значения пустые, приложение показывает экран «ForQ пока не настроен».

## Настройка Supabase

1. SQL Editor → New query → вставить `supabase/migrations/0001_init.sql` → Run.
2. SQL Editor → New query → вставить `supabase/migrations/0002_features.sql` → Run.
3. Authentication → Sign In / Providers → Email: включить провайдер и оставить `Confirm email` включённым.
4. Authentication → URL Configuration:
   - Site URL — адрес, куда возвращать после подтверждения письма.
   - Redirect URLs — список разрешённых адресов. Для разработки `http://localhost:5173/**`, для продакшена адрес страницы на Netlify, например `https://имя.netlify.app/**`. Тот же список используется для ссылки восстановления пароля, отдельного правила не нужно.

Приложение передаёт `emailRedirectTo` с текущим origin, но Supabase проигнорирует адрес, которого нет в списке Redirect URLs.

## База

Три миграции, применяются по очереди в Supabase → SQL Editor → New query → Run. Все идемпотентны, повторный запуск не ломает схему.

`0001_init.sql`:

- `profiles` — ник, био, аватар. Строка появляется через RPC `claim_username`, а не триггером на `auth.users`.
- `posts` — текст поста, `edited_at`, `deleted_at`. Удаление только мягкое: политики `DELETE` нет вообще.
- `likes`, `comments` — составные ключи и мягкое удаление комментариев.
- `feed` — представление с `security_invoker = true`: отдаёт пост вместе с ником, аватаром, счётчиками и флагом `liked_by_me`.

`0002_features.sql`:

- `comments.parent_id` — ответы на комментарии.
- `notifications` и представление `notifications_feed` — уведомления о лайках, комментариях, ответах и упоминаниях.
- `post_tags` — хештеги, разобранные из текста поста.
- Рейт-лимиты на посты, лайки и комментарии.
- Ограничения бакета `avatars`: 2 МБ и четыре типа картинок.

`0003_counters_and_pins.sql`:

- `posts.like_count` и `posts.comment_count` — денормализованные счётчики, их ведут триггеры на `likes` и `comments`. `feed` больше не считает их подзапросами. Миграция пересчитывает значения с нуля, поэтому повторный запуск заодно лечит расхождения.
- `likes.id` — `identity`-колонка, чтобы листать список лайков по порядку отметок. Первичный ключ остаётся составным `(post_id, user_id)`.
- `profiles.pinned_post_id` — закреплённый пост в профиле.

Права выдаются точечно: `revoke all` для `anon` и `authenticated`, затем `grant` на конкретные колонки (`update (body, deleted_at)`, `update (read_at)`, `update (pinned_post_id)`). Поэтому нельзя переписать `created_at` и поднять свой пост в ленте, `username` изменить через API невозможно вообще, счётчики лайков и комментариев не подделать, а уведомления нельзя вставить — на `notifications` нет права `insert`, строки создают только триггеры.

### Триггеры

| Триггер | Что делает |
| --- | --- |
| `enforce_post_rate` / `enforce_like_rate` / `enforce_comment_rate` | лимиты 5 постов, 30 лайков и 10 комментариев в минуту на пользователя. Перед подсчётом берётся `pg_advisory_xact_lock`, поэтому параллельные вставки не проскакивают мимо лимита |
| `enforce_comment_depth` | ответ на ответ схлопывается до исходного комментария, так что глубина всегда один уровень. Ответ на комментарий из другого поста отклоняется |
| `cascade_comment_delete` | мягкое удаление комментария убирает и ответы на него, поэтому `comment_count` не расходится с тем, что видно |
| `notify_*` | создают уведомления. Себе уведомления не приходят, повторный лайк после снятия не дублирует запись |
| `sync_post_tags` | пересобирает теги при вставке и при правке текста |
| `touch_post_edit` | проставляет `edited_at` при изменении текста |
| `sync_like_count` / `sync_comment_count` | держат `posts.like_count` и `posts.comment_count` в согласии с таблицами лайков и комментариев. Снятие лайка и мягкое удаление ответа вычитают, каскад удаления комментариев списывает каждый ответ ровно один раз |
| `enforce_pinned_owner` | закрепить можно только свой неудалённый пост |
| `clear_pinned_post` | удаление поста снимает закрепление |

Ошибки приходят клиенту кодами (`54000` — лимит, `23505` — ник занят, `23514` — текст не проходит проверку или закрепляют чужой пост, `42501` — нет прав), клиент переводит их в человеческие сообщения в `src/lib/api.ts`.

## Пагинация

Курсором по `id`, а не по времени и не через `OFFSET`:

```
GET feed?order=id.desc&limit=20
GET feed?order=id.desc&limit=20&id=lt.<последний_увиденный_id>
```

`id` — монотонный `identity`, поэтому порядок по нему совпадает с порядком по времени, но фильтр остаётся одним условием. Индексы `posts_feed_idx` и `posts_author_idx` частичные (`where deleted_at is null`).

Тем же курсором листаются ответы в профиле (`comments.id`) и лайки (`likes.id`). В ленте лайков подгрузка идёт по `likes.id`, а сами посты запрашиваются пачкой: если лайк остался на удалённом посте, страница добирается до полного размера, а курсор берётся от последней прочитанной строки лайка, а не от последнего найденного поста. Иначе список обрывался бы раньше времени.

## Бренд

Исходник логотипа — `branding/logo.png`: знак «QF» и подпись «ForQ» на чёрном фоне. `npm run icons` сам находит на картинке две светлые полосы (знак и надпись), берёт верхнюю, строит из неё `static/mark.png` с прозрачным фоном и уже из него собирает иконки PWA, фавиконы и `apple-touch-icon`. Ничего не нужно вырезать руками: достаточно положить новый файл на место старого и перезапустить команду.

Знак в шапке — тот же `mark.png`, но подставленный как CSS-маска поверх `currentColor`, поэтому он белый в тёмной теме и чёрный в светлой. Фон исходной картинки при этом не виден.

## Разметка текста

`src/lib/format.ts` разбирает текст поста или комментария на токены, а `RichText.svelte` рендерит их: упоминания ведут на `/u/ник`, хештеги — на `/tag/тег`. Ссылки не собираются через `{@html}`, поэтому пользовательский текст остаётся экранированным.

Хештег обрывается на пробеле и знаках препинания, регистр приводится к нижнему — `#Тест` и `#тест` попадают на одну страницу. Кириллица поддерживается. Упоминание распознаётся, только если `@` стоит на границе слова, иначе `почта@example.com` превратилось бы в ссылку на профиль `example`.

## Уведомления

Строки создают триггеры на `posts`, `likes` и `comments` — клиент не может вставить уведомление сам. Пометка «прочитано» — единственное, что доступно на запись, и только для своих строк.

Счётчик непрочитанных (`session.unread`) обновляется при смене пользователя и обнуляется при открытии `/notifications`. Список читается из представления `notifications_feed`, где подтянуты ник и аватар автора действия.

## Профиль

Три вкладки: посты, ответы и лайки. Активная вкладка живёт в адресе (`?tab=replies`), поэтому на неё можно дать ссылку. Посты листаются как везде, ответы — пачками по 20 с цитатой исходного поста, лайки — в порядке отметок.

Закреплённый пост показывается первым блоком над списком и исключается из самого списка, чтобы не повторяться. Закрепить можно только свой неудалённый пост, удаление поста снимает закрепление. Кнопка «Закрепить» есть в любой ленте, а не только в профиле.

## Черновик

Текст главного композера складывается в `localStorage` при каждом вводе и стирается при успешной публикации. Если вкладка закрылась случайно, текст вернётся в поле при следующем открытии. Черновик один на браузер и не привязан к аккаунту; ответы на комментарии не сохраняются.

## Комментарии

Верхнеуровневые комментарии пагинируются по `id` вниз по 10 штук, ответы подгружаются пачкой на уже показанных родителей и сортируются по возрастанию. Новый комментарий вставляется в список из ответа PostgREST, без перезапроса.

Вложенность ограничена одним уровнем на уровне базы, а не интерфейса: ответ на ответ схлопывается до исходного родителя. Удаление комментария убирает и ответы на него.

## PWA

Манифест и service worker лежат в `static/` и работают без привязки к хешам сборки. Стратегия — сеть вперёд, кеш только как запас: онлайн всегда отдаётся свежая версия, офлайн открывается последняя сохранённая оболочка. Кеш ограничен 150 записями, навигации по неизвестным путям откатываются на сохранённый `index.html`.

Регистрация service worker'а происходит только в продакшене — в дев-режиме он бы мешал горячей перезагрузке. Приложение можно поставить на телефон через «Добавить на главный экран»; standalone-режим, иконки и theme-color заданы в `manifest.webmanifest` и `app.html`.

## Особенности SvelteKit 3

Проект собран на SvelteKit 3, где поменялся ряд вещей относительно второй версии:

- `svelte.config.js` не используется — конфиг целиком в `sveltekit()` внутри `vite.config.ts`.
- `$lib` удалён, вместо него сабпат-импорты `#lib/*` из `package.json` → `imports`.
- `$app/stores` заменён на `$app/state`, `page` теперь обычный объект.
- Env-переменные объявляются явно в `src/env.ts` и читаются из `$app/env/public`, а не из `$env/static/public`.
- tsconfig наследуется от `$app/tsconfig` (генерируется в `node_modules/$app/tsconfig.json`).

`tsconfig.json` дополнительно прописывает `paths` для `#lib/*`, иначе TypeScript не находит эти импорты.

## Хостинг

Сайт живёт на Netlify, публикуется статика из `build/`. Всё нужное лежит в `netlify.toml` — он читается автоматически при импорте репозитория, руками в панели ничего настраивать не нужно:

| Что | Значение |
| --- | --- |
| Команда сборки | `npm run build` |
| Публикуемая папка | `build` |
| Версия Node | `22` (SvelteKit 3 требует не ниже 22.17) |
| Переменные Supabase | `[build.environment]` |
| SPA-роутинг | `[[redirects]]` и `static/_redirects` |

Правило `/* /index.html 200` отдаёт приложение на любой путь: серверного роутера у статики нет, поэтому `/u/имя` и `/p/12` должны открывать `index.html`, а маршрут дальше разбирает клиент. Файлы в `_app/immutable/` кешируются на год — имена у них хешированные, так что это безопасно.

Ключи Supabase продублированы в `netlify.toml` без ссылки на переменные окружения Netlify. Это те же публичные значения, которые всё равно уезжают в бандл браузера, поэтому секретом они не являются, зато сборка работает сразу после импорта. Если ключи поменяются, править нужно и `.env`, и `netlify.toml`.

### Почему не Cloudflare

Замеры задержки с машины в Екатеринбурге (октябрь 2026):

| Площадка | Результат |
| --- | --- |
| `*.supabase.co` | открывается, 0,09 с на соединение |
| `*.netlify.app` | открывается, 0,14 с |
| `*.github.io` | открывается, 0,18 с |
| `*.vercel.app` | таймаут |
| `*.pages.dev` | таймаут |

Cloudflare Pages и Vercel из России не открываются. При этом Supabase сам отдаётся через Cloudflare и работает — то есть режут не весь Cloudflare, а конкретные площадки. GitHub Pages тоже рабочий вариант, но там пришлось бы возиться с подпутём и отдавать `404` на прямые ссылки.

### Про подпуть

`vite.config.ts` читает переменную окружения `BASE_PATH`:

```bash
BASE_PATH=/forq npm run build
```

Все ссылки в проекте обёрнуты в `resolve()` из `$app/paths`, поэтому сборка одинаково работает и в корне домена, и в подпапке. Для Netlify переменную задавать не нужно — сайт лежит в корне.

## Что не сделано

- Капча на регистрации. При открытой регистрации включается за пару шагов: Cloudflare Turnstile в Supabase Auth → Settings → Bot and Abuse Protection, затем токен виджета передавать в `options.captchaToken` при `signUp`.
- Своя отправка писем. Встроенный SMTP Supabase не годится для реальных получателей — нужен Resend или аналог в Auth → Settings → SMTP. Без него не доходят ни подтверждение почты, ни восстановление пароля.
- Жалобы на посты и модерация.
- Абсолютные даты в постах не в локали пользователя, а в русской.
- Уведомления не приходят в реалтайме: счётчик обновляется при загрузке страницы, а не в момент события.
- Ответы на комментарий не пагинируются — грузятся целиком на показанных родителей.
- Сжатие аватара теряет анимацию GIF и делает картинку квадратной по длинной стороне.
- Нет e2e-тестов. SQL проверялся прогоном миграций и сценариев на PGlite (Postgres 17 в WASM), фронтенд — только `npm run check` и ручной обход маршрутов.

## Что решено сознательно не в пользу удобства

- Мягкое удаление комментария уносит и ответы на него. Так `comment_count` всегда совпадает с тем, что видно в ветке, а «висячих» ответов без родителя не бывает. Цена — удаление чужого ответа вместе со своим комментарием.
- Рейт-лимит на лайки (30 в минуту) может задеть того, кто листает ленту и ставит отметки подряд.
- Уведомление о повторном лайке не создаётся заново: одна запись на пару «автор — тот, кто лайкнул» на пост.
- Вкладка «Лайки» открыта всем: любой может посмотреть, что ты отметил. Это модель Twitter, а не Instagram. Закрыть доступ можно одной политикой на `likes`, но тогда вкладка останется только у себя.
- Счётчики лайков и ответов денормализованы триггерами. Чтение стало дешевле, зато запись дороже на один `update`, а расхождение теперь возможно и лечится повторным прогоном `0003`.
